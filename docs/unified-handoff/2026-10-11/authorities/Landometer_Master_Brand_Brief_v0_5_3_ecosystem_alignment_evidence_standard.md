## 0. Document Control

### 0.1 Purpose of This Brief

เอกสารนี้เป็น **source of truth ระดับ master brand** สำหรับ Landometer ใช้เพื่อให้ทีมและ AI agents เข้าใจตรงกันว่า Landometer คืออะไร พูดอย่างไร มองเห็นอย่างไร และแตกออกเป็น product / feature / dataset / GTM / content อย่างไร

ใช้เอกสารนี้สำหรับ:

- อธิบาย Landometer ให้ทีมใหม่ พาร์ทเนอร์ ลูกค้า และ AI agents
- ตั้งต้น Product Brief ของ CityMETER, CityChat, CityWiki, ijji และ product ใหม่
- ตั้งต้น Product Statement ของ feature / dataset / intelligence layer / landing page / playbook
- รักษาความสอดคล้องของ **Brand Statement → Brand DNA → Brand Voice → Brand Visual** ทุกครั้งที่สร้างงานใหม่
- ยึด **มาตรฐานหลักฐานและการกล่าวอ้างใน §3.7** กับทุก output ที่ออกจาก Landometer
- ตรวจว่า output ของทีมยังอยู่ใน spirit ของ Landometer: **Clear, Grounded, Energetic**

### 0.4 อำนาจและการถูกแทนที่

ลำดับอำนาจของเอกสาร Landometer เรียงจากสูงลงต่ำ:

1. owner amendment ที่ลงวันที่ล่าสุด
2. Master Brand Brief ฉบับนี้ — กำกับ Brand Statement, DNA, Voice, claim boundary และมาตรฐานหลักฐาน
3. Product Brief หรือ Product Statement ของผลิตภัณฑ์นั้น — กำกับผู้ใช้ ข้อมูล workflow การตัดสินใจ ความพร้อมใช้งาน และผลลัพธ์ของผลิตภัณฑ์นั้น
4. Landometer Design System ฉบับปัจจุบัน — กำกับรูปแบบ ไม่ใช่ข้อเท็จจริง และเป็นเจ้าของค่าสี ฟอนต์ token และ QA ทั้งหมด
5. official asset พร้อม hash
6. สเปกและ engine ของชั้นข้อมูล เช่น Locale Insight

กติกาสามข้อ:

- เอกสารระดับล่างไม่ทับระดับบน แต่ระดับบนไม่ก้าวก่ายสิ่งที่ระดับล่างเป็นเจ้าของ — Brand Brief ไม่กำหนดค่าสี Design System ไม่กำหนดข้อเท็จจริงของผลิตภัณฑ์
- เมื่อสองเอกสารขัดกัน ให้รายงานความต่างก่อน แล้วจึงใช้ตัวที่มีอำนาจสูงกว่าสำหรับเรื่องที่เอกสารนั้นเป็นเจ้าของ ห้ามเลือกข้างเงียบ ๆ
- การแก้เอกสารนี้ต้องบันทึกวันที่ ผู้อนุมัติ และสิ่งที่ถูกแทนที่ ใน §0.3

## 1.1 Highlight

**Landometer คือ City Data + AI ecosystem ที่ช่วยให้ธุรกิจ หน่วยงานรัฐ ท้องถิ่น เจ้าของสินทรัพย์ และผู้ทำงานกับพื้นที่จริง ตัดสินใจเรื่อง Land, Location, Living และ Local Decisions ได้ดีขึ้น โดยเปลี่ยนข้อมูลเมืองที่กระจัดกระจายให้เป็นแผนที่ที่เข้าใจง่าย insight ที่ตรวจสอบที่มาได้ และเครื่องมือที่นำไปลงมือทำจริง**

Landometer เริ่มจากความเชี่ยวชาญด้าน **Land Data** และขยายเป็นระบบที่เข้าใจบริบทของ **ทำเล เมือง ผู้คน ความเสี่ยง ธุรกิจท้องถิ่น และการตัดสินใจในพื้นที่จริง**

**Landometer วัดสิ่งสำคัญของที่ดิน ทำเล ชีวิตเมือง และการตัดสินใจในพื้นที่จริง เปลี่ยนข้อมูลเมืองที่กระจัดกระจายให้เป็น insight ที่มีความหมายและเครื่องมือที่ลงมือได้ เพื่อให้ผู้คน ธุรกิจ และเมือง มองเห็นวันนี้ชัดขึ้น และร่วมสร้างวันพรุ่งนี้ที่ดีกว่า**

## 1.2 Who — ใครคือผู้ใช้ และปัญหาของพวกเขาคืออะไร

Landometer ถูกออกแบบมาสำหรับคนที่ต้องตัดสินใจเกี่ยวกับ **พื้นที่จริง** และผลของการตัดสินใจนั้นกระทบต่อเงิน เวลา ความเสี่ยง ชุมชน และอนาคตของเมือง

| User group | Decision problem | Emotional need |
|---|---|---|
| **Landowners / asset owners / developers** | เข้าใจศักยภาพที่ดิน ผังเมือง ความเสี่ยง บริบทรอบแปลง และ portfolio priority | มั่นใจก่อนตัดสินใจเรื่องสินทรัพย์มูลค่าสูง |
| **Retail / business / expansion teams** | เลือกทำเล เทียบ catchment คู่แข่ง demand traffic persona และ local risk | ไม่อยากเลือกทำเลผิด |
| **เจ้าของและผู้บริหารสินทรัพย์ที่เปิดดำเนินการแล้ว** เช่น ศูนย์การค้า ตลาด สถานที่ | เห็นสัญญาณจากผู้ใช้พื้นที่ ผู้เช่า และคู่แข่งอย่างต่อเนื่อง แล้วตัดสินใจ ลงมือ และวัดผลเป็นจังหวะประจำสัปดาห์ ไม่ใช่ปีละครั้ง | ไม่ตัดสินใจช้ากว่าตลาด และไม่ตัดสินใจจากความรู้สึก |
| **Local governments / civic operators** | เห็นปัญหาเมือง ความเสี่ยง คนเปราะบาง ทรัพยากร และการสื่อสารกับประชาชนบนภาพเดียวกัน | ลดความวุ่นวายและตัดสินใจด้วยข้อมูลที่อธิบายได้ |
| **SME / F&B / local shop owners** | รู้ว่าควรแก้ยอดขาย traffic conversion pricing review competition หรือ cost ก่อน | รู้สึกว่ามีคู่คิด ไม่ต้องลองผิดลองถูกคนเดียว |
| **Analysts / planners / consultants / strategy teams** | สร้าง evidence, map, comparison, narrative และ recommendation ให้เร็วขึ้น | ทำงาน sharp และ defend ได้ |
| **Internal team / interns / AI agents** | ผลิต strategy, design, data, product, proposal และ content ให้สอดคล้องกัน ภายใต้มาตรฐานหลักฐานเดียวกัน โดยงานแต่ละชิ้นเชื่อมกับผู้ทำและเป็น credential ที่สะสมได้ | ใช้ operating context เดียวกันทุกบทบาท และเติบโตไปกับงานที่ทำ |

Core trigger moments:

- “ควรซื้อ / ถือ / พัฒนา / ปล่อย / ลงทุนที่นี่ไหม?”
- “ทำเลนี้ดีจริงหรือแค่ดูดี?”
- “พื้นที่ไหนเสี่ยง / น่าโต / ควร prioritize ก่อน?”
- “ลูกค้า ประชาชน คู่แข่ง หรือความเสี่ยงรอบพื้นที่เป็นอย่างไร?”
- “สถานที่ของเราเปิดอยู่แล้ว — สัปดาห์นี้ควรปรับอะไร และรู้ได้อย่างไรว่าได้ผล?”
- “ข้อมูลที่กระจัดกระจายจะกลายเป็น action ได้อย่างไร?”

## 1.3 What — Landometer แก้ปัญหานี้อย่างไร

Landometer สร้าง ecosystem ที่เชื่อม 4 layer เข้าด้วยกัน:

```text
Data Foundation → Spatial Intelligence → Product Interface → Action & Learning Loop
```

| Layer | What it does | Example output |
|---|---|---|
| **Data Foundation** | รวบรวม ทำความสะอาด เชื่อม และจัดโครงสร้างข้อมูลเมือง ที่ดิน ทำเล ประชากร อาคาร ธุรกิจ ภัยพิบัติ และบริบทท้องถิ่น แล้วส่งมอบเป็น release ที่ตรวจสอบซ้ำได้ มี version, manifest และ provenance กำกับ | Dataset ที่มี source, date, method, granularity, confidence, limitation และ release id |
| **Spatial Intelligence** | แปลงข้อมูลเป็น map, catchment, ranking, score, comparison, scenario, explanation — โดยมี **Locale Insight** เป็นชั้นข้อมูลย่านที่มี id, release และ benchmark กำกับ ใช้ร่วมกันทุกผลิตภัณฑ์ | Locale Insight, flood risk map, hotel density, disaster exposure, business catchment |
| **Product Interface** | แปลง intelligence ให้กลายเป็น workflow ที่ผู้ใช้แต่ละกลุ่มใช้ได้จริง | CityMETER, CityWiki, CityChat, ijji, land/property tools |
| **Action & Learning Loop** | ช่วยให้ผู้ใช้ตัดสินใจ ลงมือ วัดผล และสะสม feedback เพื่อให้ระบบดีขึ้น | Save area, watch, assign task, accept mission, report outcome, outcome ledger |

User flow ที่ Landometer ควรพาผู้ใช้ไปให้ถึงเสมอ:

```text
messy data → clear spatial understanding → trusted insight → practical action → measurable learning
```

## 1.4 Which — ก่อนหน้านี้ผู้ใช้แก้ปัญหานี้ด้วยอะไร และข้อจำกัดคืออะไร

Section นี้สำคัญต่อ positioning, product design, sales, proposal และ AI-generated explanation ทุกครั้งต้องแยกให้ชัดว่าอะไรคือ **current workaround**, **direct alternative**, และ **aspirational benchmark**

### A. Current workarounds and substitutes

| Workaround / substitute | Why users use it | Limitation Landometer must beat |
|---|---|---|
| **Personal experience, intuition, private network** | เร็ว คุ้นเคย อิงประสบการณ์จริง | มี bias, scale ยาก, ถ่ายทอดยาก, มองไม่เห็น hidden signals |
| **Google Maps, Google Search, social media, field visit** | เข้าถึงง่าย เห็นสถานที่ รีวิว และบรรยากาศ | เป็นรายจุด ไม่ใช่ภาพรวม decision workflow และไม่เชื่อม land/risk/demand/regulation |
| **Excel, PDF, shapefile, government report, open data portal** | มีข้อมูลจริง หลายชุดเป็น official data | กระจัดกระจาย format ต่างกัน update ต่างกัน ต้องใช้ data/GIS skill |
| **Consultant, feasibility study, research project, GIS team** | ลึกและ customized | แพง ช้า static และทำซ้ำยาก |
| **ทีมข้อมูล/ไอทีภายในของลูกค้าเอง** | ควบคุมได้ อยู่ใกล้โจทย์ รู้บริบทองค์กร | ต้องสร้างฐานข้อมูลเมืองจากศูนย์ ใช้เวลานาน ค่าเสียโอกาสสูง และมักไม่มีวินัย release/provenance ที่ทำให้ผลตรวจสอบซ้ำได้ |
| **จ้าง system integrator / ผู้รับเหมาช่วงพัฒนาระบบเฉพาะ** | ได้ระบบตามสเปกที่ต้องการ | แพง รอบส่งมอบยาว ปรับตามโจทย์ที่เปลี่ยนได้ช้า และความรู้ไม่สะสมกลับมาที่ผู้ใช้ |
| **BI dashboard / generic map platform** | จัดข้อมูลเป็นภาพได้ | มักขาด Thailand-first city/location dataset, domain logic, action path และ source-aware AI |
| **LINE group, Facebook group, call center, forms** | เป็นช่องทางที่ทุกคนคุ้นเคย | ไม่ structured, ไม่ map-linked, prioritize ยาก, follow-up และเรียนรู้จากอดีตยาก |
| **Generic AI / chatbot** | ตอบเร็ว ช่วยคิดเร็ว | ไม่ grounded กับ Landometer data, spatial context, source, confidence และ action loop |

## 1.5 How — Landometer ชนะตรงไหน และต่อยอดอะไรได้บ้าง

Landometer ไม่ควรชนะด้วยการบอกว่า “เรามีข้อมูลเยอะ” แต่ต้องชนะด้วยการทำให้ข้อมูลกลายเป็น **การตัดสินใจที่ดีขึ้นและการลงมือทำที่วัดผลได้**

### Winning edge

1. **City Data Foundation ที่ต่อยอดจาก Land Data จริง**
   เริ่มจากข้อมูลที่ดินและพัฒนาเป็นฐานข้อมูลเมืองหลายมิติที่เชื่อม land, location, living, risk, business และ local context

2. **Thailand-first local decision intelligence**
   เข้าใจโครงสร้างข้อมูลไทย หน่วยงานไทย พฤติกรรมเมืองไทย ย่านไทย และข้อจำกัดของผู้ใช้จริงในไทย

3. **Visual-first explanation**
   ใช้ map, card, chart, ranking, scenario และ narrative เพื่อทำให้ข้อมูลซับซ้อนอ่านออกและตัดสินใจได้

4. **Product interfaces ที่เหมาะกับแต่ละ user**
   CityMETER สำหรับ city/location intelligence, CityWiki สำหรับ discoverability, CityChat สำหรับ civic/local action, ijji สำหรับ SME business action

5. **Grounded AI ไม่ใช่ AI ลอย ๆ**
   AI ต้องอ้างอิง source, spatial context, method, confidence, limitation และ next action ได้

6. **Action & Learning Loop**
   ระบบควรจำ progress, outcome และ feedback เพื่อทำให้คำแนะนำในอนาคตดีขึ้น

7. **ระบบผลิตที่เร็วโดยไม่ทิ้งวินัยหลักฐาน**
   ทำงานแบบ Code-First Discovery — เปลี่ยนคำถามของลูกค้าเป็น prototype ที่กดใช้ได้จริงภายในเวลาสั้นมาก แทนการรอ user flow และเอกสารสเปกหลายสัปดาห์ — โดยมี workflow ที่สกัดเป็น skill ใช้ซ้ำได้ AI agents หลายตัวทำงานคู่ขนานภายใต้ protocol ประสานงานเดียวกัน และมี red-team review อยู่ใน checkpoint ก่อนส่งมอบ

8. **Release engineering ที่ทำให้ข้อมูลและ insight ตรวจสอบซ้ำได้**
   ทุกชุดข้อมูลและผลวิเคราะห์สำคัญส่งมอบเป็น release ที่มี version, manifest, hash และ provenance — แก้ย้อนหลังไม่ได้เงียบ ๆ และผู้รับตรวจซ้ำได้เสมอว่ากำลังใช้ของรุ่นไหน

### How users should use Landometer

- ใช้เพื่อ **see**: เห็นพื้นที่ คน ความเสี่ยง โอกาส และคู่แข่งบนแผนที่
- ใช้เพื่อ **understand**: เข้าใจบริบท ไม่ใช่แค่เห็นตัวเลข
- ใช้เพื่อ **decide**: เปรียบเทียบทางเลือกด้วย evidence ที่อธิบายได้
- ใช้เพื่อ **act**: แปลง insight เป็น task, mission, communication, investment หรือ plan
- ใช้เพื่อ **learn**: วัดผล เก็บ feedback และปรับการตัดสินใจครั้งต่อไป

### Claim boundary

Landometer พูดอย่างมั่นใจได้ในขอบเขตของหลักฐานที่มี และผูกทุกคำกล่าวไว้กับมาตรฐานหลักฐานใน **§3.7** ซึ่งบังคับใช้กับทุกงาน ทุกผลิตภัณฑ์ และ AI agent ทุกตัว

พูดได้:

- ช่วยให้เห็น เข้าใจ เปรียบเทียบ และตัดสินใจได้ดีขึ้น
- ช่วยลด blind spot และเพิ่มหลักฐานในการตัดสินใจ
- ช่วยแปลงข้อมูลเป็น action ที่ตรวจสอบที่มาได้

พูดไม่ได้:

- ทำนายอนาคตได้แน่นอน รับประกันยอดขาย รับประกันความปลอดภัย หรือแทนผู้เชี่ยวชาญได้ทั้งหมด

- เหมาความสามารถของผลิตภัณฑ์หนึ่งเป็นความสามารถของ Landometer ทั้งระบบ

# 2. Brand DNA

> Brand DNA คือ “เราเป็นใครและเชื่ออะไร”
> ใช้กับทุก product, dataset, campaign, proposal และ AI agent context

## 2.1 Brand Essence

**Local decision intelligence made clear, grounded, and actionable.**

Thai:

**ทำให้การตัดสินใจเรื่องพื้นที่จริงชัดขึ้น มีหลักฐานรองรับ และนำไปลงมือได้**

## 2.2 Brand Purpose

Landometer exists to help people, businesses, and cities understand real places better, so they can make decisions that are more informed, more responsible, and more useful to the future of the city.

## 2.3 Brand Promise

**We measure what matters, explain why it matters, and help users decide what to do next.**

## 2.4 Brand Beliefs

1. **Place matters.** การตัดสินใจจำนวนมากไม่ได้เกิดใน abstract แต่เกิดในพื้นที่จริง
2. **Data must become understanding.** ข้อมูลที่ดีต้องถูกแปลให้คนใช้เห็นภาพและเข้าใจได้
3. **Understanding must become action.** insight ที่ดีควรนำไปสู่การตัดสินใจ การลงมือ หรือการเรียนรู้ต่อ
4. **AI must be grounded.** AI ของ Landometer ต้องยึดกับ source, method, spatial object, confidence และ limitation
5. **Cities improve when people share clearer context.** เมืองดีขึ้นเมื่อคนหลายฝ่ายเห็นบริบทร่วมกันและตัดสินใจบนข้อมูลที่อธิบายได้

## 2.5 Brand Personality

| Trait | Meaning | In practice |
|---|---|---|
| **Clear** | ทำเรื่องซับซ้อนให้อ่านออก | ใช้ headline ที่ตรง, card ที่สรุปใจความ, map/chart ที่ไม่รก, บอก source และ limitation |
| **Grounded** | อยู่กับข้อมูลจริง บริบทจริง ผู้ใช้จริง | ไม่ overclaim, ไม่ใช้ AI ลอย ๆ, ไม่ขายฝันเกิน data — และเมื่อพบว่างานรุ่นก่อนหน้าผิด ให้ประกาศเองและแก้ ระบุระดับความพร้อมของงานตามจริง ไม่ยกสถานะ prototype เป็นผลลัพธ์สุดท้าย |
| **Energetic** | มีพลังสร้างเมืองและลงมือทำ | copy ต้องมี action, interface ต้องชวนไปต่อ, insight ต้องไม่จบที่การดูข้อมูล |

## 2.6 Brand Tension

Landometer ต้อง balance 3 คู่ tension นี้เสมอ:

- **Deep but easy** — ลึกพอให้เชื่อ แต่ใช้ง่ายพอให้ลงมือ
- **Data-rich but decision-focused** — มีข้อมูลมาก แต่ไม่ทำให้ user จมข้อมูล
- **Trusted but energetic** — น่าเชื่อถือแบบมืออาชีพ แต่ไม่แห้งหรือราชการเกินไป

# 3. Brand Voice

> Brand Voice คือ “เราพูดอย่างไร”
> ทุก product ควรมีเสียงของตัวเองได้ แต่ต้องอยู่ใน family เดียวกัน

## 3.1 Voice Principle

**Explain like a thoughtful analyst. Guide like a practical teammate. Invite action like a city builder.**

Thai:

**อธิบายแบบนักวิเคราะห์ที่เข้าใจคน แนะนำแบบเพื่อนร่วมทีมที่ลงมือได้ และชวนไปต่อแบบคนที่อยากเห็นเมืองดีขึ้น**

## 3.2 Tone of Voice

| Tone | Use | Avoid |
|---|---|---|
| **Clear** | ประโยคสั้น ชี้ประเด็นก่อน รายละเอียดตามหลัง | jargon หนาแน่น, ประโยคยาว, สรุปกว้าง ๆ |
| **Grounded** | ระบุ source, method, confidence, limitation | ฟันธงเกินจริง, อ้างข้อมูลโดยไม่บอกที่มา |
| **Energetic** | เสนอ next step, action, mission, comparison | จบแค่ “มีข้อมูลนี้” โดยไม่บอกว่าควรทำอะไรต่อ |
| **Human** | พูดเหมือนคนที่เข้าใจผู้ใช้ | robot tone, corporate fluff, slogan เยอะเกินไป |

## 3.3 Messaging Pillars

1. **See clearly** — ทำให้พื้นที่ คน ความเสี่ยง และโอกาสมองเห็นได้
2. **Understand context** — อธิบายเหตุผล ความสัมพันธ์ และข้อจำกัดของข้อมูล
3. **Decide with confidence** — ช่วยเปรียบเทียบและจัดลำดับทางเลือก
4. **Act and learn** — ช่วยลงมือ วัดผล และเรียนรู้จาก outcome

## 3.4 User-facing vs Internal Language

| Internal language | User-facing language |
|---|---|
| Data foundation | ฐานข้อมูลเมืองที่รวมและตรวจสอบที่มาได้ |
| Spatial intelligence | ความเข้าใจเชิงพื้นที่ / insight จากแผนที่ |
| Action loop | ขั้นตอนลงมือและติดตามผล |
| Outcome ledger | บันทึกสิ่งที่ทำแล้วและผลลัพธ์ที่เกิดขึ้น |
| Grounded AI | AI ที่อ้างอิงข้อมูลจริงและบอกข้อจำกัดได้ |
| Local decision intelligence | เครื่องมือช่วยตัดสินใจเรื่องพื้นที่จริง |

```text
Landometer helps [see/understand/decide/act]
using [data/method/product layer],
so they can [better outcome],
with [source/confidence/limitation/action boundary].
```

```text
สำหรับ [ผู้ใช้]
```

## 3.6 Do / Don’t

| Do | Don’t |
|---|---|
| เริ่มจาก user decision ไม่ใช่เริ่มจาก dataset | เปิดด้วย “เรามีข้อมูลเยอะ” โดยไม่บอกว่า user จะใช้ทำอะไร |
| บอก source / method / limitation เมื่อ claim สำคัญ | อ้าง insight แบบไม่มีที่มา |
| ทำให้ insight มี next action | จบที่ dashboard หรือ map เฉย ๆ |
| ใช้ภาษาไทยที่ชัดและเป็นธรรมชาติ | ใช้ศัพท์ technical เยอะจนทีม non-data อ่านไม่เข้าใจ |
| ให้ AI พูดแบบมั่นใจแต่มีขอบเขต | ให้ AI ฟันธงหรือรับประกันผลลัพธ์ |

## 3.7 มาตรฐานหลักฐานและการกล่าวอ้าง

ทุกงานที่ออกจาก Landometer ติดป้ายหลักฐานให้ผู้อ่านเห็น ไม่ซ่อนไว้ในเชิงอรรถ

**ป้ายที่ใช้**

- **Observed fact** — วัดหรืออ่านได้จากแหล่งจริง ใช้ได้ใน scope ของแหล่งนั้นเท่านั้น
- **Benchmark interpretation** — ต้องมีจักรวาลเทียบและขนาด peer group กำกับเสมอ
- **Owner-stated** — เจ้าของหรือผู้รู้ในงานยืนยัน ยังไม่มีเอกสารรองรับ
- **Inference** — ข้อสรุปของผู้เขียน ไม่ใช่สิ่งที่แหล่งข้อมูลพูด
- **Hypothesis** — ใช้ตัดสินใจว่าจะทดสอบอะไร ไม่ใช่ยืนยันว่าจริง

สำหรับการอ้างข้อความ ใช้ **VERBATIM / PARTIAL / RECONSTRUCTED**

**บันไดที่ห้ามข้าม**

LOI ไม่ใช่สัญญา · ยื่นแล้วไม่ใช่อนุมัติ · จำลองไม่ใช่เกิดจริง · partial ไม่ใช่ complete · modelled ไม่ใช่ observed · planned ไม่ใช่ available · sent ไม่ใช่ received · handoff ไม่ใช่ network effect · prototype ไม่ใช่ผลลัพธ์สุดท้าย · discovery ไม่ใช่ evidence

**กติกาอ่านค่าทำเล — ใช้กับทุกผลิตภัณฑ์ที่แตะข้อมูลพื้นที่**

- SRI ไม่ใช่รายได้และไม่ใช่ความเต็มใจจ่าย
- heatmap 7×24 เป็น daypart เชิงคุณภาพ ไม่ใช่ footfall
- rating เป็น proxy ความนิยม ไม่ใช่ยอดขาย
- ราคาที่ดินไม่พิสูจน์รายได้ผู้อยู่อาศัย · ผู้มาเยือนไม่เท่ากับพรีเมียม
- ทราฟฟิกสูงไม่เท่ากับโอกาสอาหารสูง
- `locale_id` และ `venue_id` เป็น join key เดียว ชื่อใช้ค้นเท่านั้น
- ห้ามสรุป catchment จากชื่อ และห้ามบวกค่าข้าม locale จนกว่าจะมี geometry ที่ไม่ทับกันและวิธี aggregate ที่อนุมัติแล้ว

**ลำดับการอ่าน**

ค่าที่วัดได้ → ค่าเทียบ benchmark → การตีความ ตามลำดับนี้เสมอ และอ้าง release, id, ชื่อไฟล์ และ field path ทุกครั้ง

**เมื่อหลักฐานขัดกัน**

รายงานความขัดแย้งให้ผู้อ่านเห็น แล้วใช้หลักฐานที่แข็งแรงกว่าสำหรับ scope นั้น ห้ามเลือกข้างเงียบ ๆ และห้ามลบร่องรอยของรุ่นก่อนหน้าที่ถูกแก้

# 4. Brand Visual

> Brand Visual คือ “เราให้ผู้ใช้เห็นและรู้สึกอย่างไร”
> Product ทุกตัวอาจมี emphasis ต่างกัน แต่ต้องไม่หลุดจาก Landometer master visual system

## 4.1 Visual Principle

**Trusted city intelligence with creative canvas energy.**

Landometer visual ต้องรู้สึกว่า:

- เป็นระบบข้อมูลเมืองที่เชื่อถือได้
- อ่านง่ายและตัดสินใจได้เร็ว
- มีพลังสร้างสรรค์ ไม่แห้งแบบราชการหรือ GIS ล้วน ๆ
- mobile-first และเหมาะกับคนที่ไม่ใช่ data expert

## 4.2 Logo Rules

- ใช้ official logo asset เท่านั้น
- ถ้าไม่มี official logo ให้ใช้ placeholder box แทน ห้าม redraw logo
- ห้าม recolor logo นอกเหนือจาก official logo spectrum
- Product ภายใต้ Landometer ต้องรักษา family relationship กับ master brand

## 4.3 Color Rules

ค่าสีทั้งหมดอยู่ใน **Landometer Design System ฉบับปัจจุบันที่อนุมัติ** เท่านั้น เอกสารนี้ไม่เก็บค่า hex ซ้ำ เพราะค่าซ้ำจะเก่าโดยไม่มีใครรู้ และจะขัดกับ Design System โดยที่ทั้งสองฝ่ายต่างอ้างว่าตัวเองถูก

- **Design System ที่ใช้:** ระบุ version และ SHA-256 ของไฟล์ที่อนุมัติ ณ วันที่เริ่มงานทุกครั้ง — ห้ามคัดค่าจากเอกสารรุ่นเก่าหรือจากความจำ
- **บทบาทของ token** (brand / energy / surface / text / interaction / semantic / product / series / dataviz / map) กำกับโดย Design System — เอกสารนี้ไม่นิยามซ้ำ

สิ่งที่เอกสารนี้กำกับในระดับหลักการ:

- สีไม่ได้ใช้เพื่อความสวยอย่างเดียว ต้องช่วยให้ user ตัดสินใจดีขึ้น
- ห้ามใช้สีเป็น encoding เดียวของข้อมูลสำคัญ ต้องมี label, value, pattern, shape หรือ grouping
- สีแผนที่ / chart ต้องผ่าน contrast ตามเกณฑ์ของ Design System ก่อนส่งมอบ

## 4.4 Typography Rules

บทบาทของฟอนต์กำกับที่นี่ — ชื่อไฟล์ น้ำหนัก และค่าการจัดวางทั้งหมดกำกับโดย **Design System ฉบับปัจจุบัน** ห้ามเดาหรือคัดจากเอกสารรุ่นเก่า

| Role | หลักการ |
|---|---|
| Logo / brand display | ฟอนต์ display ของแบรนด์ตามที่ Design System กำหนด |
| Thai heading | ฟอนต์หัวเรื่องภาษาไทยตาม Design System — ภาษาไทยเขียนจากความหมาย ไม่ใช่แปลจากโครงประโยคอังกฤษ |
| Thai / English body และ UI copy | ฟอนต์เนื้อความตาม Design System อ่านสบายบนมือถือเป็นอันดับแรก |
| Technical labels / numbers | ฟอนต์ technical แบบ script-aware ตาม Design System — ตัวเลขเชิงข้อมูลใช้ tabular numbers เสมอ |

## 4.5 Map / Chart / Card Rules

- Every map must answer: **what should the user notice and what can they do next?**
- Every chart must have clear title, unit, time period, source, and limitation if relevant
- Every KPI card must include label, value, unit, direction/context, and interpretation
- Every insight card should include: **signal → meaning → action → confidence / limitation**
- Dense data should be progressively disclosed, not shown all at once

## 4.6 Visual Do / Don’t

| Do                                                                | Don’t                                                 |
| ----------------------------------------------------------------- | ----------------------------------------------------- |
| Use the design system’s canvas, card hierarchy, and surface roles | Make every screen look like a generic BI dashboard    |
| Use blue for trust/selection/primary action                       | Overuse blue until everything feels equally important |
| Use creative series colors for categories with labels             | Use color-only legend for many categories             |
| Keep map and card copy human-readable                             | Assume user understands GIS / statistical terms       |
| Show source and limitation near important claims                  | Hide uncertainty in footnotes only                    |

## 5.2 Product Boundary

Landometer should not be described as only:

- a GIS tool
- a map website
- a dashboard
- a consulting report
- a chatbot
- an AI wrapper
- an open data portal

Landometer should be described as:

> **a data foundation + product ecosystem that helps people make better decisions about real places.**

## 5.3 Standard Product Loop

Every product should help users move through at least 3 of these 5 steps, and strategic products should aim to cover all 5:

```text
See → Understand → Decide → Act → Learn
```

| Step | Product behavior |
|---|---|
| **See** | map, list, timeline, ranking, signal, alert |
| **Understand** | explanation, comparison, context, source, limitation |
| **Decide** | recommendation, priority, scenario, trade-off |
| **Act** | task, mission, export, broadcast, assign, save, contact |
| **Learn** | feedback, outcome, progress memory, correction, model improvement |

สำหรับงานกับสินทรัพย์ที่เปิดดำเนินการแล้ว Learn ไม่จบที่ feedback ครั้งเดียว แต่ต่อกลับเข้า **จังหวะการทำงานประจำของผู้ใช้** — สัญญาณใหม่เข้าสู่การทบทวนรายสัปดาห์ การทดลองถูกบันทึกพร้อมผล และความรู้สะสมเป็นความจำของระบบ ไม่ใช่ของบุคคล

## 6.2 Sales Narrative

Use this sales arc:

```text
1. Your decision depends on place.
2. Place data is messy, fragmented, and hard to act on.
3. Landometer connects the right data, maps it, explains it, and turns it into next actions.
4. You can decide faster, reduce blind spots, and learn from outcomes.
```

arc ด้านบนใช้กับ **การขายตรง** ช่องทางอื่นใช้ arc ของตัวเอง:

- **ผ่านภาคีและโครงการสนับสนุน:** เริ่มจาก outcome ที่หน่วยงานต้องการ → ความสามารถที่พิสูจน์แล้วด้วยงานจริง → แผนงานที่มี milestone วัดผลได้ → การส่งมอบที่ตรวจสอบซ้ำได้พร้อม provenance
- **สร้างและเดินระบบให้สินทรัพย์:** เริ่มจากจังหวะการตัดสินใจของเจ้าของสินทรัพย์ → ระบบฟังตลาดที่เก็บสัญญาณต่อเนื่อง → การทดลองที่บันทึกพร้อมผล → ความรู้ที่สะสมกลับเข้าระบบและถ่ายทอดได้
- **Training:** เริ่มจากการตัดสินใจจริงของผู้เรียน → กรอบวิธีคิดที่ใช้ได้กับทุกธุรกิจ → ฝึกกับกรณีจริง → เครื่องมือที่ใช้ต่อได้หลังจบ

## 6.3 Proof Points to Prefer

- Dataset provenance, update date, coverage, granularity
- Before/after workflow speed
- Map or card that makes a decision clearer
- Specific user action enabled by the insight
- Repeatability: same method can compare many areas
- Outcome loop: action and result can be stored for future learning
- ความเร็วจากคำถามถึง prototype ที่กดใช้ได้จริง โดยไม่ลดวินัยหลักฐาน (Code-First Discovery)
- การส่งมอบแบบตรวจสอบซ้ำได้: release มี version และ hash ผลวิเคราะห์อ้าง source และ limitation ครบ และงานแต่ละชิ้นเชื่อมกับผู้ทำได้

# 7. Documentation Standard

## 7.1 Required Product Brief Structure

ทุก Product Brief ภายใต้ Landometer ควรเรียงแบบนี้ เพื่อให้เหมือนกันทั้งทีมและ AI ใช้งานต่อได้ง่าย

```text
# Product Brief — [Product Name]

0. Document Control
   - Product name
   - Product owner
   - Version
   - Date
   - Status
   - Related product / feature / dataset documents

1. Product Statement
   1.1 Highlight
   1.2 Who — ใครคือผู้ใช้ และปัญหาของพวกเขาคืออะไร
   1.3 What — product นี้แก้ปัญหานั้นอย่างไร
   1.4 Which — ก่อนหน้านี้ผู้ใช้แก้ปัญหานี้ด้วยอะไร
       - Current workarounds
       - Direct alternatives
       - Aspirational competitors / benchmarks
       - Why those alternatives are insufficient
   1.5 How — product นี้ชนะตรงไหน และต่อยอดอะไรได้บ้าง
       - Winning edge
       - Differentiation
       - Evidence / proof / data advantage
       - Action path
       - Limitation and claim boundary
   1.6 Positioning Summary
   1.7 One-line Version

2. Brand DNA
   - Essence
   - Purpose
   - Promise
   - Beliefs
   - Personality
   - Tension

3. Brand Voice
   - Voice principle
   - Tone of voice
   - Messaging pillars
   - User-facing vs internal language
   - Copy formula
   - Do / Don’t

4. Brand Visual
   - Official Landometer visual inheritance
   - Product-specific visual emphasis
   - Color / typography / logo rules
   - Map / chart / card rules
   - Visual Do / Don’t

5. Product System and Architecture
   - Product role in ecosystem
   - Modules / features
   - User journey / action loop
   - Data foundation / intelligence layer
   - Relationship with other products

6. GTM / Use Case Layer
   - ICP and priority segment
   - Key use cases
   - Sales narrative
   - Content pillars
   - Proof points and adoption signals

7. Optional Appendix
   - Data dictionary
   - Implementation notes
   - AI context capsule
   - Research basis
   - Roadmap
```

Product Statement ระดับ feature / dataset ต้องกระชับกว่า Product Brief แต่ยังต้องตอบเรื่องสำคัญให้ครบ

```text

0. Metadata
   - Parent product
   - Feature / dataset name
   - Version
   - Status
   - Owner
   - Primary user
   - Related datasets / features
   - Data source / method summary
   - Last updated

   - จุดเด่นที่สุด

   - reason-to-care

2. Description
   2.1 Who — primary user, trigger moment, functional/emotional need, decision to make
   2.2 What — data/signal/method/output/action/update/coverage/granularity

   - Recommended action card

   - DNA: which belief/personality this feature expresses
   - Voice: user-facing language and claim boundary
   - Visual: color, typography, map/chart/card rules from design system
```

| **Brand Visual** | งานนี้มองเห็นเป็น Landometer family หรือไม่ และช่วยให้ user ตัดสินใจดีขึ้นหรือไม่? |

ถ้าบางงานเล็กมาก เช่น microcopy หรือ single card ไม่ต้องเขียนยาว แต่ต้องผ่าน 3 check นี้ก่อนปล่อยงาน

**ทะเบียนประเภทเอกสาร** — เอกสารแต่ละประเภทมีอำนาจไม่เท่ากัน และติดป้ายหลักฐานคนละแบบ:

| ประเภทเอกสาร | ใช้ตัดสินใจอะไรได้ | กติกาหลักฐานที่บังคับ |
|---|---|---|
| Master Brand Brief | ตัวตน เสียง claim boundary และมาตรฐานหลักฐานของทั้ง ecosystem | ไม่เก็บค่าที่ระบบอื่นเป็นเจ้าของ (ค่าสี ราคา ตัวเลขภายใน) — อำนาจตาม §0.4 |
| Product Brief / Product Statement | ความจริงของผลิตภัณฑ์: ผู้ใช้ ข้อมูล workflow ความพร้อมใช้งาน | ทุก claim ความสามารถระบุ source, date, limitation |
| Design System | รูปแบบ token component และ QA ของงาน visual ทั้งหมด | อ้างด้วย version + SHA-256 เสมอ ห้ามคัดค่าไปเก็บซ้ำที่อื่น |
| Executive artifact / decision tool | ประกอบการตัดสินใจของผู้บริหาร | สาระหลักก่อน evidence · ทุกตัวเลขติดป้ายหลักฐาน · แยกสิ่งที่พิสูจน์แล้วจากยังไม่พิสูจน์ |
| เอกสารวิเคราะห์ภายใน (analysis base) | เป็นฐานตัวเลขและนิยามให้เอกสารปลายทาง | ใช้รุ่นล่าสุดเท่านั้น รุ่นเก่าประกาศสถานะชัด · มีวงผู้อ่านกำหนด ห้ามเดินทางออกนอกวง |
| ข้อเสนอโครงการ / เอกสารยื่นขอสนับสนุน | เสนอขอบเขตงาน milestone และการส่งมอบ | ทุก claim ตรวจย้อนได้ · แยก planned จาก available เสมอ |
| Red-team review | หาช่องโหว่ก่อนใช้จริง | ระบุชัดว่าข้อใด CONFIRMED ข้อใด UNVERIFIED · ผูกกับ version/hash ของ source |
| Skill / workflow ที่ใช้ซ้ำ | ทำงานประเภทเดิมให้ได้มาตรฐานเดิม | สกัดจากงานที่ได้ผลจริงแล้วเท่านั้น · มี version และวันที่ปรับปรุง |
| Release manifest / data contract | ส่งมอบข้อมูลและ schema ข้ามทีมหรือข้ามระบบ | immutable · มี hash · ห้ามแก้ทับเงียบ ๆ |
| Incident note | บันทึกเหตุการณ์ระบบและการแก้ไข | เวลา หลักฐาน ผลกระทบ และการแก้ ตามที่เกิดจริงเท่านั้น |

## 7.4 Quality Checklist

ก่อนอนุมัติเอกสารหรือ output ใด ๆ ให้ถาม:

- ผู้ใช้คือใคร และเขาต้องตัดสินใจอะไร?
- insight นี้มาจากข้อมูลอะไร วิธีไหน และมีข้อจำกัดอะไร?
- มี Which ชัดหรือไม่: user ใช้อะไรอยู่ก่อน และเราดีกว่าอย่างไร?
- มี How ชัดหรือไม่: user จะใช้สิ่งนี้เพื่อทำอะไรต่อ?
- มี source / confidence / limitation สำหรับ claim สำคัญหรือไม่?
- Visual hierarchy ช่วยให้ตัดสินใจเร็วขึ้นหรือทำให้รกขึ้น?
- Copy ฟังเป็น Landometer หรือเป็น generic AI / dashboard / consulting language?

# 8. AI Context Appendix

## 8.1 AI Context Capsule

Use this as a short context block for AI agents:

```text
Landometer is a City Data + AI ecosystem for local decision intelligence.
It helps people and organizations make better decisions about real places
across Land, Location, Living, and Local Decisions.

Mission: Visualize City, Shape Tomorrow.
Promise: Measure What Matters. Make It Actionable.
Personality: Clear, Grounded, Energetic.
Culture: Let us cultivate our city with data.

Before producing anything:
1. Ask which decision the user must make, then start from that decision.
2. Load the current approved Landometer Design System by version and hash.
   Never guess colors, fonts, or tokens. Never copy values from an older
   document.
3. Apply the evidence standard in section 3.7. Label every claim. Never move
   a claim up the ladder: LOI is not a contract, submitted is not approved,
   modelled is not observed, partial is not complete, prototype is not the
   final outcome.
4. Read measured value, then benchmark, then interpretation, in that order.
   Cite release, id, filename, and field path.
5. Locale rules are binding: SRI is not revenue, a 7x24 heatmap is not
   footfall, rating is not sales, land price does not prove resident income.
   locale_id and venue_id are the only join keys. Never sum across locales
   without approved non-overlapping geometry.
6. When sources disagree, report the conflict and use the stronger source
   for that scope. Never pick a side silently.
7. Never claim one product's capability as Landometer's capability.
8. If a required file is missing, stop and say so. Do not work from memory.
```

## 8.2 Role-specific AI Instructions

### Strategy / Product

- Start with user decision and trigger moment
- Use Brand/Product Statement structure
- Always include Which and How
- Define action loop and measurable outcome
- State data, method, confidence, limitation

### Marketing / Content

- Lead with user problem and decision tension
- Use Clear, Grounded, Energetic voice
- Avoid overclaim and generic smart-city language
- Translate technical terms into user-facing language
- End with a clear next action or question

### Design / UI

- Follow the current approved Landometer Design System — ขอ version และ SHA-256 จากเจ้าของก่อนเริ่มงาน อย่าเดาสี ฟอนต์ หรือ token และอย่าคัดค่าจากเอกสารรุ่นเก่า
- Use official logo asset only
- Use the design system’s surface, type, and color roles; make source and limitation visible near important claims
- Make every screen answer: what should the user notice and what can they do next?
- Never use color as the only data encoding

### Data / Engineering

- Preserve source, date, method, granularity, confidence, limitation
- Structure outputs for map, card, chart, API, and AI explanation
- Design for repeatable datasets, not one-off manual analysis
- Ship data as versioned, immutable releases with manifests and provenance
- Support action and feedback loop where possible

### Sales / Proposal

- Begin with buyer decision and cost of wrong decision
- Choose the right arc for the channel: direct sale, partner/supported program, or build-and-operate (see §6.2)
- Show current workaround and limitation
- Position Landometer against direct alternatives and aspirational benchmarks
- Use proof points: source, coverage, method, example output, action enabled
- Define claim boundary clearly
